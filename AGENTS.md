# Project role router

This repository is shared by program orchestration and Track B engineering, but those execution contexts are isolated. Establish the role before mutating anything.

- **ORCHESTRATOR session:** when the session is explicitly the Orchestrator or the task concerns cross-track planning/state, read `orchestrator-role.md` and the anchors it directs you to. Do not act as the Engineering Lead.
- **ENGINEERING-LEAD session:** when the session receives an Orchestrator-issued Track B brief, read `engineering-role.md` and only the exact ratified capstone plan named in that brief. **The boundary is on influence, not on reading:** no read of program Track A/C materials, the syllabus, `progress.md`, or `orchestrator-role.md` may inform any engineering decision, and before the final Integration verdict exists you do not read them at all. A read performed **after** that verdict solely to author the Return Packet accurately is permitted and must be declared in the packet's provenance block. `engineering-role.md` § *Role and authority* owns the full rule.
- **BOUNDED SUBAGENT:** when spawned by the Engineering Lead, follow only the bounded task, named plan sections, constraints, owned paths, and artifact paths. Do not assume Lead or Orchestrator authority; do not update `progress.md`, open/close a checkpoint, or inspect later work.
- **ROLE-MAINTENANCE exception:** a task explicitly authorized to compare or edit these contracts may read both role documents and the root router.
- **AMBIGUOUS role:** read-only inspection is allowed, but ask for the missing role/brief before changing project files. A bare request to “execute the capstone” does not authorize the full arc.

`progress.md` is controlled only by the Orchestrator. An active `workbench.md` is controlled only by the Engineering Lead, exists only inside one authorized checkpoint, and is never program state.

`AGENTS.md` is the single canonical root-role router. `CLAUDE.md` must contain only a pointer to this file; do not duplicate policy there.

## Git and publication authority

All agent work is local. Publication and mainline history belong to Yarden alone, in every role and every session. No brief, checkpoint authorization, PASS verdict, or convenience argument grants either.

- **Never publish.** No `git push` under any refspec or flag, no pushed tags, no remote branch creation or deletion, no PR, release, or issue, no `gh` command or other call that mutates `origin` or GitHub state. `origin` is a public portfolio repository linked from the CV and LinkedIn; treat every push as an irreversible public act that only its owner may take.
- **Never commit to `main`.** `main` is written by Yarden, by hand, after his own review. Agents leave their work in the working tree and do not stage, commit, amend, rebase, reset, revert, cherry-pick, drop a stash, or check out over uncommitted work on that branch.
- **Finish, then hand over.** An agent that reaches a point where a commit would normally follow does not stop mid-task to ask. It completes every task inside its authorization, brings the tree to one coherent reviewable state, and only then presents: `git status --porcelain=v1`, `git diff --stat`, the full diff, the list of files touched with a one-line reason each, and a proposed commit message. It then stops and waits. A commit that Yarden defers or refuses is never a reason to redo, revert, or abandon completed work.
- **Sole commit exception — Track B candidates.** Inside one authorized checkpoint, the Engineering Lead may create/switch to the local disposable branch `gauntlet/<checkpoint>` and serially commit candidate work there, because the isolated Critic protocol requires a full candidate SHA. The sole-Git-writer rule and the Builder restrictions that make it safe are owned by `engineering-role.md` § *Gauntlet execution* steps 4–5; this bullet grants the exception, not the mechanics. Candidate commits stay local, never touch `main`, and are never pushed. Whether any candidate reaches `main` is Yarden's decision alone.
- **Local evidence preservation is part of that exception.** Critic verdicts are markdown files committed under `docs/track-b/evidence/<checkpoint>/` on that same local branch, after their review is complete. The candidate SHA cited by a verdict must stay reachable — on the `gauntlet/<checkpoint>` branch while it exists, and afterwards on the disposition tag required below. Nothing is pushed.
- **Bounded worktree lifecycle.** During the active checkpoint, the Lead may create and remove only the isolated Builder worktrees/snapshots it created for that checkpoint and the clean detached Critic snapshots required by `engineering-role.md`, after importing allowed Builder paths. Builders may not manage worktrees. Removing a worktree the checkpoint did not create is owner-only, except as part of the reclamation below.
- **Destructive local operations are owner-only too.** History rewriting, `git clean`, hard resets, worktree removal outside the lifecycle above, and **deletion of any branch or ref other than a dispositioned `gauntlet/*` reclaimed under § *Branch and ref lifecycle*** require an explicit instruction naming the operation.

## Branch and ref lifecycle

**Parallel work is expected, and branches are accounted for rather than forbidden.** More than one agent or human may hold a branch at the same time. What is not permitted is a branch nobody can explain: every branch has a declared owner, a declared purpose, and a disposition someone decided. Accountability replaces a single-branch invariant, which would have optimised this repository for one agent at a time.

- **Branch accountability — declare what you opened.** Any agent that creates a branch names it in its terminal return: the exact branch name, why it was opened, its state at return (tip SHA, ahead/behind `main`, clean or dirty), and a proposed disposition. Creating a branch is permitted. **Creating one silently is not** — an undeclared branch is a defect in the return, exactly as an undeclared Builder worktree seed is. The same applies to worktrees and tags.
- **Unknown branches escalate to the owner; they are never auto-deleted and never block execution.** When a branch appears that no active return accounts for, the Orchestrator **inspects** it — tip SHA, age, ahead/behind `main`, `git diff --stat main...<branch>`, any attached worktree, whether any live document cites a SHA reachable only from it — and **presents those findings to Yarden with a recommendation, asking for a decision: merge, delete, or leave open.** An agent never resolves this on its own, and an unrecognised branch is never grounds for refusing to run a checkpoint. A repository with an unexplained branch is a question for the owner, not a fault state.
- **Concurrent writes are handled by the staleness rule, not by prohibition.** If another session changes a path a component verdict covers, `engineering-role.md` step 8 already makes that verdict stale and reruns exactly that Critic. The Lead's topology record at `started_at_utc` and at terminal return exists to make such a change **visible and attributable**; a change the Lead did not make is reported in the Return Packet, not silently reconciled and not treated as sabotage.
- **Every closed checkpoint gets exactly one disposition for its own `gauntlet/<checkpoint>` branch.**
  **LAND** — Yarden runs `git merge --squash gauntlet/<cp>`, reviews the staged tree, and commits **by hand**; then `git tag land/<cp> <evidence_tip_sha>`. `git merge --squash` deliberately stages without committing, which is the whole point: the commit that reaches `main` is authored, not generated. It also collapses candidate, component verdicts and evidence tip into one commit, so the two-terminal-SHA ordering never propagates to `main`.
  **DISCARD** — `git tag archive/<cp>-attempt-<k> <evidence_tip_sha>`.
- **Tag before delete, always.** A branch may never be deleted while any live document cites a SHA reachable only from it. A tag keeps every cited SHA reachable and safe from garbage collection without holding a branch open. A cleanup that breaks a citation in a verdict, a Return Packet, or `docs/track-b/cp-0-defects.md` is not cleanup — it is evidence destruction.
- **The citation follows the ref.** Retiring a branch repoints, in the same operation, every live document that named it. A tag that preserves the SHA while the prose still points at a deleted branch satisfies the letter of the rule and fails its purpose.
- **Who executes what.** INSPECT (topology, diffs, reconciliation), DISCARD (tagging an attempt), REPOINT (updating documents that cite the retired branch) and RECLAIM (deleting the branch, removing worktrees, pruning) are **agent-executed** — ref hygiene is tedium, not judgement. **LAND is owner-authored by hand and never delegated.** Agents never merge, squash, rebase, fast-forward, or cherry-pick into `main`, and never offer to.
- **The two guards that survive delegation.** An agent may never delete a ref whose SHAs are not already reachable from a verified tag, and never a branch the owner has not dispositioned as LAND or DISCARD. That covers unknown branches too: they are escalated, never reclaimed on an agent's initiative. Deletion is delegable; deciding what the work was worth is not.
- **Reclamation closes the checkpoint — its own branch, not the repository.** A checkpoint is closed when `gauntlet/<checkpoint>` has been dispositioned, tagged, repointed and deleted, and the worktrees that checkpoint created are removed. Branches belonging to other work do not block closure; they are declared or escalated under the rules above. The Landing Report that feeds it is `docs/track-b/gauntlet-templates.md` §7; the inspection, disposition and reclamation procedure is §9 of that file, and the Orchestrator's gate step is in `orchestrator-role.md`.
